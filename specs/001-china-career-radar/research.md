# Phase 0 Research: China Career Radar

**Date**: 2026-08-27  
**Scope**: runtime stack, persistence/queue patterns, DeepSeek contract, source governance, SSRF, Telegram.

## Runtime and framework

**Decision**: Target Node.js 24 LTS and NestJS 11.x with strict TypeScript and CommonJS output.

**Rationale**: Node 24 is the current production LTS. NestJS 12 was released on the research date and changes the default module/testing shape; NestJS 11 provides a mature greenfield baseline that still runs cleanly on Node 24 and keeps Jest integration simple. The application remains compatible with a later Nest 12 migration.

**Alternatives considered**: Node 26 is Current until October 2026; Node 22 is maintenance LTS; NestJS 12 is too fresh for the first operational iteration; NestJS 10 is established in `apps/tonem-server` but needlessly starts a new application one major behind.

## Persistence and migrations

**Decision**: PostgreSQL 18, `drizzle-orm` 0.45.x with `pg`, committed SQL migrations generated by `drizzle-kit`, and `pg_trgm` only for Possible Duplicate suggestions.

**Rationale**: PostgreSQL is the single durable store required by the product. Drizzle provides typed queries without a heavy generated client. Production uses reviewed `generate`/`migrate`, never schema `push`. Exact constraints provide the final idempotency boundary.

**Alternatives considered**: Prisma matches one neighboring app but adds a generated layer and would deviate from the requested lightweight default. Similarity-based auto-merge was rejected because a false merge destroys opportunity history.

## Durable work

**Decision**: Use pg-boss 12.x in its own `pgboss` schema with explicit queues, retry budgets, dead-letter queues, Asia/Shanghai schedules, and graceful shutdown. Synchronous CLI demonstration uses the same handlers directly.

**Rationale**: pg-boss keeps schedules and durable work in PostgreSQL and supports transaction adapters, retry backoff, DLQ, and cron without Redis. Handlers still rely on database uniqueness because delivery can repeat after a crash.

**Alternatives considered**: Redis/BullMQ adds a second required datastore. In-process timers are not durable. Multiplying provider-internal and queue retries was rejected; one persisted provider-call budget is authoritative.

## Testing

**Decision**: Jest 30 with ts-jest 29.4, explicit imports from `@jest/globals`, a separate typecheck command, in-memory contract doubles for default tests, and opt-in PostgreSQL/live-provider suites.

**Rationale**: The prompt explicitly chooses Jest and default tests must remain offline. Type checking is not delegated to transpilation. Shared adapter/repository contracts make the vertical pipeline deterministic without hiding the real PostgreSQL path used by Docker Compose.

**Alternatives considered**: Vitest matches `apps/tonem-server`, but the explicit product default wins. Native ESM Jest remains avoidable complexity for this MVP.

## Telegram library

**Decision**: Use grammY 1.x with long polling behind the project `Notifier` interface.

**Rationale**: grammY tracks the current Telegram Bot API, while Telegraf v4 is beyond its announced support window. Long polling requires no public ingress and fits the private control-plane decision.

**Alternatives considered**: Telegraf is functional but stale. Webhooks require public HTTPS and secret-token validation, which are outside the MVP boundary.

## DeepSeek API and validation

**Decision**: Use `POST /responses` with `deepseek-v4-flash`, `reasoning.effort: none`, and `text.format.type: json_schema`. Validate the response envelope, extract only completed `output_text`, parse JSON, apply strict Zod validation, then apply deterministic policy invariants.

**Rationale**: Responses API schema output is stronger than Chat Completions `json_object`. Local validation is still required for score/verdict alignment, evidence presence, bounded fields, and Work Permit rules. Store response ID, model, status, latency, and token counts; never store reasoning.

**Alternatives considered**: Chat Completions JSON mode can return empty content and guarantees syntax rather than the domain schema. It remains a possible future fallback adapter, not the default.

## DeepSeek retry policy

**Decision**: Default 90-second deadline and at most three provider calls across queue attempts. Retry network/timeouts, 429, 500, 503, empty/malformed/schema-invalid output, and one bounded max-token failure. Do not retry 400, 401, 402, 422, or content-filter outcomes.

**Rationale**: A single persisted budget prevents multiplicative retry explosions. Exhausted work moves to dead-letter and can never notify.

**Alternatives considered**: SDK retries were rejected because they hide attempt accounting. Persisting raw invalid output was rejected because it may contain sensitive or reasoning content.

## Analyzer privacy

**Decision**: Send only a redacted vacancy plus capability projection. Do not send candidate IDs, citizenship/immigration facts, contacts, institution names, child/family data, or recruiter personal data. Use an opaque HMAC subject. Compute legal/profile constraints locally.

**Rationale**: DeepSeek's privacy policy permits retention and training use and describes PRC processing; `store: false` is not a zero-retention guarantee. Data minimization is the only safe default.

**Alternatives considered**: Sending the full stored profile would improve convenience but disclose unnecessary personal and immigration data irreversibly.

## Safe URL retrieval

**Decision**: Route every network acquisition through `SafeHttpFetcher`: exact policy gate before DNS, WHATWG URL parsing, HTTPS by default, no credentials or unsafe ports, all-address DNS validation, pinned connection lookup, manual redirects revalidated per hop, 10-second deadline, 1 MiB streaming limit, MIME allowlist, no cookies/auth/proxy state, and no automatic retries.

**Rationale**: Preflight DNS followed by ordinary fetch has a check/use race. OWASP guidance requires allowlists, all A/AAAA validation, redirect control, and DNS-rebinding defenses. Egress firewalling remains defense in depth.

**Alternatives considered**: regex validation, RFC1918-only blocking, first-address checks, global fetch with automatic redirects, and unpinned second DNS resolution all leave known SSRF bypasses.

## Source policy and ChinaJob

**Decision**: A versioned strict YAML policy gates each acquisition mode independently. ChinaJob is `policyStatus: pending`, `allowedModes: [fixture]`, and `live.enabled: false`.

**Rationale**: RFC 9309 states robots.txt is not access authorization. ChinaJob publicly exposes `/job/` and allows it in robots.txt, but no affirmative reuse terms, API, or license were found. Written permission is required before live aggregation.

**Alternatives considered**: Treating public access or robots Allow as permission violates the product constitution. One-time `manual_url` does not inherit permission from fixture or discovery modes.

## ChinaJob fixture parser

**Decision**: Keep the parser pure and transport-free, driven by minimized saved list/detail fixtures and a manifest recording source URL, capture date, hash, redactions, and policy note. Required selector drift raises a typed parser error.

**Rationale**: Offline fixtures prove the adapter contract without network or policy ambiguity. Canonical URLs retain `jobid` and remove pagination; visible `J...` identifiers are preferred source job IDs.

**Alternatives considered**: CI fixture refresh and live parser tests are disabled because they introduce nondeterminism and unauthorized network behavior.
